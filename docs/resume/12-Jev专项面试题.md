## Part 1 Jev 是什么

### Q1.1 什么是 Jev？
**参考答案：**
「Jev 是一个 **System One（快思考）决策模型**，由 TypeSafe AI 于 2026 年发布。
它和 LLM 最大的区别是：**它不生成文本**，只返回**类型化的决策原语**——
选择（CHOICE）、评分（SCORE）、校准布尔概率（NOUL）。
一句话：**LLM 负责『生成』，Jev 负责『判断』**。」

**追问：System One 是什么意思？**
借鉴心理学「快思考/慢思考」：System One 是直觉、快速、廉价的判断；
System Two 是深思、缓慢、昂贵的推理（LLM 擅长）。Jev 补上了前者。

### Q1.2 Jev 相比 LLM 有什么优势？
**参考答案（官方公开数据，需注明来源）：**
- **更快**：官方称约 **193×**；
- **更便宜**：官方称成本约为对照的 **1/444.6**；
- **输出稳定**：类型化结果 + 校准置信度，天然适配结构化决策，减少幻觉；
- 训练方式：RLCD（基于对比的强化学习）。
> ⚠️ 这些数字来自官方宣传，面试时建议说明「据官方公开信息」并补一句「实际以场景压测为准」。

### Q1.3 为什么「不生成文本」反而是优势？
**参考答案：**
很多判断任务根本不需要生成能力（是否完成、难度多少、相关性高低）。
让 LLM 去做这些，既慢又贵还有幻觉。Jev 把这类判断**专门化**：
输出空间极小（几个原语）+ 校准概率 → 快、稳、省。

## Part 2 原语与机制

### Q2.1 Jev 的三种原语分别是什么？
**参考答案：**
| 原语 | 含义 | 项目用途 |
|---|---|---|
| `CHOICE` | 从候选集中选一个 | 选择下一个动作/工具 |
| `SCORE` | 输出 [0,1] 打分 | 难度评分、相关性评分、质量评分 |
| `NOUL` | 校准布尔概率（是/否 + 置信度） | 是否安全、是否完成 |

### Q2.2 什么是「校准置信度」？为什么重要？
**参考答案：**
校准（Calibration）指模型给出的概率**与实际频率吻合**——
说 0.8 的事，真的约 80% 成立。
对**阈值决策**（如风险 > 0.9 就拦截）至关重要：概率若不准，阈值就没有意义。
LLM 的概率往往**过度自信**，而校准模型更适合直接设阈值。

### Q2.3 NOUL 这个名字怎么理解？
**参考答案：** 可理解为「归一化的、带不确定度的布尔判定」——
不仅回答「是/否」，还给出「有多确信」，让调用方可以按置信度做阈值/分级处理。

### Q2.4 CHOICE 和 SCORE 如何配合？
**参考答案：**
先用 SCORE 给候选打分（如各工具/各模型的适配度），再用 CHOICE 取最优。
本项目里 `JevRouter` 用 SCORE 评难度 → 映射模型档位；
`JevContextCompactor` 用 SCORE 给历史打分 → 保留 Top-K。

## Part 3 在项目中的定位

### Q3.1 为什么要把决策层单独抽出来（jev-decision-layer）？
**参考答案：**
「决策」和「生成」是两类完全不同的负载：前者高频、可缓存、要稳定；后者低频、重算力。
抽出来有三个好处：
1. **可替换**：将来 Jev 升级/换模型，不影响生成链路；
2. **可观测**：每个决策都能独立打点、独立评测；
3. **可降本**：把大模型调用从「每步都调」降为「只在生成时调」。

### Q3.2 五个决策组件是怎么分工的？

```mermaid
flowchart LR
    REQ["请求"] --> G["Guardrail<br/>NOUL 安全"]
    G --> R["Router<br/>SCORE 难度"]
    R --> ACT["生成/工具"]
    ACT --> V["Verifier<br/>NOUL 完成"]
    V --> C["Compactor<br/>SCORE 相关性"]
    C --> GR["Grader<br/>SCORE 质量"]
```

每个组件只做一件事，输入输出类型化，**可单独测试、单独替换**。

### Q3.3 每步都调 Jev 会不会成为新的瓶颈？
**参考答案：**
不会，这正是决策下沉的意义：
- Jev 判断是**毫秒级**且**便宜**，替代的是「调用大模型来判断」这一昂贵操作；
- 项目里决策层还有**离线兜底**，即使远程 Jev 抖动也不阻塞主流程；
- 后续可加**本地缓存**（相同判断结果复用）进一步降本。

## Part 4 工程接入

### Q4.1 怎么接入真实 Jev？
**参考答案：**
只需配置，不改代码：
```yaml
jev:
  fallback-local: false        # 关闭离线兜底
  api-key: ${JEV_API_KEY}
  base-url: https://api.typesafe.ai/v1
```
`JevAutoConfiguration` 会按配置装配 `RemoteJevClient` 替换 `LocalJevClient`。
这体现了**面向接口编程 + 可替换**的设计。

**追问：为什么要有离线兜底？**
① 无外部依赖即可 clone 运行、可测试、可演示；
② Jev 官方 API 尚未对中国大陆开放；
③ 生产环境可作为**降级方案**，远程 Jev 不可用时仍能判断。

### Q4.2 离线兜底是怎么实现的？它「准」吗？
**参考答案：**
`LocalJevClient` 是**确定性启发式**实现：
- 安全判定：对**被判定主体 input** 做风险关键词匹配；
- 完成判定：检测观测文本中的 done/completed 等标记；
- 难度/相关性：基于长度、词重叠等信号打分。
它**不追求聪明**，只追求**可运行、可测试、行为确定**，接口与真实 Jev 完全一致。

### Q4.3 接入 Jev 时踩过什么坑？
**参考答案（真实项目经历）：**
「护栏一开始**恒拦截所有请求**，正常请求也 BLOCKED。
根因是离线实现把 **instruction 文本也纳入了风险词扫描**，
而 instruction 本身含 unsafe/injection/jailbreak 这些词 → 恒命中。
修复方式是**只扫描被判定主体 input**，并用 instruction 的语义词区分『安全判定』和『完成判定』。
这个 Bug 让我认识到：**决策的语义边界划分，比算法本身更重要**。」

### Q4.4 如何保证接入 Jev 后的稳定性？
**参考答案：**
① 超时控制（`jev.timeout-ms`）；② 远程不可用自动降级到本地兜底；
③ 决策结果纳入 trace 可回溯；④ 用评测门禁回归决策质量。

## Part 5 对比与边界

### Q5.1 Jev 能替代 LLM 吗？
**参考答案：**
不能，也**不应该**。二者是**分工**：Jev 做「判断」（选哪个、多少分、是否完成、是否安全），
LLM 做「生成」（写答案、写代码、写文案）。把判断交给 Jev 是为了**让 LLM 只做它最擅长的事**。

### Q5.2 Jev 和小模型（如 7B）做分类有什么区别？
**参考答案：**
- 小模型是**通用生成模型**，做分类要 prompt + 采样，输出不够稳定、有幻觉；
- Jev 是**专用决策模型**，直接输出类型化原语 + 校准概率，**稳定、可设阈值、更省**。
本质是「专用 vs 通用」的取舍。

### Q5.3 Jev 的局限/风险？
**参考答案：**
① **不可生成**，复杂开放推理不行；② 依赖**校准质量**，校准差则阈值失效；
③ 新模型生态/API 成熟度待观察；④ 官方 API 区域限制。
**工程对策**：只在**边界清晰的判断任务**上用，且保留兜底与阈值可调。

### Q5.4 决策层会不会引入「级联错误」？
**参考答案：**
存在风险（如路由错→用错模型）。缓解：
① 关键决策双阈值/复核；② 决策结果记录并评测；③ 高风险动作不依赖单一判断；④ 离线兜底保证不断链。

## Part 6 深挖与开放题

### Q6.1 如果让你设计一个「决策模型」，你会怎么设计？
**参考答案框架：**
① **收敛输出空间**（原语化，避免自由文本）；
② **加入校准**（训练/后处理让概率可信）；
③ **专用化**（一个模型/头负责一类判断）；
④ **低延迟**（小参数量、可量化、可缓存）；
⑤ **可观测**（每次决策打点）。

### Q6.2 如何评估 Jev 决策的质量？
**参考答案：**
- 对 CHOICE：准确率 / 与人工标注一致率；
- 对 SCORE：与标注分数的相关性（如 Spearman）、分档准确率；
- 对 NOUL：**校准曲线**（Brier score / ECE）；
- 端到端：接入后的任务成功率、成本、延迟变化。

### Q6.3 Jev 与「Function Calling / 结构化输出」的关系？
**参考答案：**
Function Calling 让 LLM 输出结构化调用，本质还是 LLM 生成；
Jev 是**把决策本身从 LLM 剥离**出去，由专用模型直接产出，更专、更省、更稳。
二者可以互补：Jev 决定「是否以及调用什么」，LLM 负责「如何组织参数/生成内容」。

### Q6.4 如何向面试官解释「为什么这个选择有前瞻性」？
**参考答案：**
「Agent 的成本和质量瓶颈在『每步都调大模型做判断』。
行业趋势是**把决策与生成解耦**：生成继续用强 LLM，判断下沉到又快又省的专用模型。
Jev 是这个方向的代表，我的项目把它做成了**可插拔的决策层**，
既能吃到这个红利，又通过离线兜底保证不被新技术的区域/生态限制卡住。」

### Q6.5 Jev 概念题速答卡
| 问 | 一句话答案 |
|---|---|
| Jev 是什么 | System One 决策模型，不生成文本，输出类型化原语 |
| 三种原语 | CHOICE / SCORE / NOUL |
| 最大优势 | 快（官方 ~193×）、省（官方成本约 1/444.6）、稳 |
| 与 LLM 关系 | 判断 vs 生成，分工不替代 |
| 项目怎么用 | 决策层 5 组件：护栏/路由/校验/压缩/评分 |
| 怎么接入 | 配置 fallback-local=false + api-key，零改代码 |
